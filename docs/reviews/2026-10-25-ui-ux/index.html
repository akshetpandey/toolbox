Keep these strengths

  • The privacy message is prominent, understandable, and appropriate for the product. No account or signup wall interrupted the tested tasks.
  • Selected-file names, sizes, dimensions, and previews provide useful context. Switching tools within a category preserves the selected file.
  • Aspect-locked resize correctly updated height when width changed. A 350 × 208 image exported at 700 × 416.
  • PDF pointer reordering worked and the order summary updated. Two PDFs containing one and two pages produced a three-page merged document.
  • Archive creation shows the exact output filename before processing. Extraction exposes individual file downloads and a download-all action.
  • DOCX and the synthetic XLSX both converted successfully. The Office success screen gives a clearer completion state than the image and video tools.
  • Checksum values wrap on phone layouts, a matching expected checksum is recognized, and a mismatch produces explicit No match text.
  • Keyboard focus rings are visible, the Choose file button opens with Enter, and the current page link exposes aria-current.

Overall design direction: calm, capable, and easy to finish

The app already has an approachable identity, useful previews, familiar controls, and a strong reason to exist: private file processing without an account. Its current presentation feels more like a collection of component examples than one finished product. Large rounded cards, nested borders, soft shadows, repeated navigation, and changing action colors compete for attention. The next design pass should make the current task, file, and outcome immediately clear. A modern appearance will come from consistent hierarchy, restrained surfaces, and confident interaction states.

Keep the simple Toolbox identity, recognizable category icons, plain-language privacy promise, file details, and immediate access without signup. Use the existing components as a foundation, then reduce the number of competing treatments.

Four principles for a more coherent product

  1. Give each screen one clear job — Name the actual task in the page heading: Resize image, Merge PDFs, or Convert document to PDF. Put the selected file and the next action in the same visual reading path. Category navigation, theme controls, project links, and advanced options should be quieter.
  2. Make the file the working material — Before selection, make the picker inviting and specific about accepted files. After selection, replace the large drop zone with a compact file summary. Give the saved space to the preview, canvas, ordered document list, or relevant controls.
  3. Make the next step predictable — Use a shared progression: choose file, adjust, process, inspect result, download. Simple tasks can process and download in one action, but should still leave a visible result and Download again. Avoid a wizard that adds clicks to a two-field task.
  4. Design each screen for its available space — Use a phone layout with its own navigation and control order. Expand into useful columns on larger screens only when each column has enough room. Keep task state when a layout changes.

A practical visual system

The values below are proposed starting points for a design pass. Test them with real content, long filenames, both themes, and enlarged text; they are not measurements of the current implementation.

Area Current design critique Suggested direction Why it helps
Hierarchy and page titles Image Tools and repeated category navigation dominate while the active task is mostly identified by a tab. Lead with the task name, a short purpose sentence when needed, a compact selected-file row, then the working controls. Use one dominant action per stage. Keep secondary actions such as Replace and Reset visibly secondary. A visitor can identify the task and next step without scanning two navigation systems.
Typography Headings, field labels, metadata, and helper text do not consistently distinguish the task from surrounding interface chrome. Use one UI type family with a deliberate scale: roughly 28–32 px task headings on desktop, 24–28 px on phones, 16 px body and input text, and 14 px labels or secondary metadata. Use 1.4–1.6 line height and reserve semibold for headings, labels, and key values. Keep filenames readable; use monospace only where useful, such as hashes. Clearer scanning, fewer tiny labels on phones, and a more intentional visual rhythm.
Spacing and density The upload panel and nested cards consume substantial space even when the remaining task is just a few fields. Use a 4/8 px spacing scale as a starting point: about 16 px phone gutters, 24–32 px desktop gutters, 8–12 px within related controls, 16 px between field groups, and 24–32 px between sections. Keep useful whitespace around the task while reducing padding inside nested containers. Controls become easier to associate without making the screen feel crowded or sparse.
Surfaces, borders, and depth Multiple large rounded surfaces, inset dashed frames, and soft shadows give similar prominence to every region. Use a neutral page background and one main work surface. Separate internal groups with alignment, spacing, or a fine divider. Reserve dashed borders for a drop target awaiting files, shadows for overlays or a deliberately raised surface, and a restrained 8–12 px corner radius for most containers. The working content becomes the focal point and the interface feels cleaner and more precise.
Color and brand Primary actions change from purple to blue to green across tools, while category colors and status colors add more competing signals. Choose one primary action color, with the existing blue as a practical starting point. Keep category tints in small icons or navigation accents. Use green for success, amber for caution, and red for errors or destructive actions, always with text or an icon explaining the meaning. People learn one action language while the category identity remains recognizable.
Controls and icons Button sizes, long labels, icon-only actions, and small tabs create inconsistent emphasis and touch comfort. Define shared primary, secondary, quiet, and destructive button styles. Align input and button heights around 44–48 px where appropriate, including their hit areas. Prefer concrete verbs such as Resize image or Merge 3 PDFs. Keep Lucide icon size and stroke treatment consistent, pair unfamiliar icons with text, and provide visible focus, selected, disabled, and loading states. Actions look related, are easier to hit, and explain what will happen.
Dark mode The dark trim screen retains a pale pink error surface that feels disconnected from the surrounding theme. Create explicit dark tokens for page, surface, border, muted text, focus, and semantic states. Give error and success messages compatible dark surfaces. Check text, control, and focus contrast in both themes rather than mechanically inverting colors. Dark mode feels designed and status messages remain legible without excessive glare.
Motion and perceived quality Loading, navigation, and completion need a consistent interaction language; performance was not benchmarked in this review. Use brief, purposeful transitions, around 150–200 ms as a starting point, for drawers and status changes. Respect reduced motion, retain focus, and avoid shifting the primary action during loading. Show Preparing video, Processing, and Ready as distinct states; use indeterminate progress when no reliable percentage exists. The interface communicates progress without making the person wait through decoration or misread what is running.

Make the experience easier from start to finish

Turn the homepage into a useful starting point

Lead with a short benefit such as Private file tools, right in your browser, followed by a clearly labeled task search and popular tasks: Resize image, Compress image, Merge PDFs, Convert to PDF, and Extract archive. Show category groups below. Keep the privacy reassurance near the first action; move release history, implementation libraries, and project links lower. A first-time visitor should be able to choose a task immediately. Search should match everyday terms such as shrink photo as well as tool names.

Related detailed findings: 04, 05, 17.

Use familiar goals before technical parameters

Prefill real image dimensions and valid video ranges. Offer understandable presets such as Smaller file, Balanced, and Best quality, with a short explanation of the tradeoff. Put CRF, codec, encoder speed, and other expert settings in Advanced. Show units, output format, and the effect of a setting near the control. Keep advanced settings available for people who need precision.

Related detailed findings: 08, 13.

Give each workflow an appropriate work area

Use a large canvas with a compact wrapping toolbar for redaction; a timeline, playback preview, and valid start/end controls for trim; an ordered list with filenames and page counts for PDF merging; and clear name, type, size, and download actions for archives. Share navigation, file summaries, buttons, and status patterns across tools while allowing their main work areas to differ.

Related detailed findings: 01, 03, 09, 19.

Treat completion as a product screen

Retain a result summary showing the filename, format, size, and relevant dimensions, duration, or page count. Offer Download again and a clear next task that can reuse the result when supported. Compression should show before and after sizes and percentage change, including a neutral explanation when the result is larger. Distinguish the source file from the generated output. Avoid claiming a file was saved to disk when the app can only initiate a download.

Related detailed findings: 06, 15.

Make recovery and privacy understandable

Use plain-language errors with the most useful next action: Choose another file, Change settings, or Try again. Put raw diagnostics in an optional details area. Preserve completed edits when navigating where practical; otherwise warn before discarding them. Explain what Remove metadata affects, and label actions separately when they only remove a file from the current workspace. Keep the local-processing reassurance short and close to file selection.

Related detailed findings: 07, 10, 14, 16.

Make accessibility part of the shared interaction model

Use one focus stop per action, named navigation and main regions, accessible names for icon controls, and a logical focus order. Make selected states and validation understandable without color. Announce processing, completion, and errors without stealing focus. Provide keyboard alternatives to dragging PDFs or drawing where feasible, and verify zoom, text enlargement, long filenames, and narrow layouts alongside pointer use.

Related detailed findings: 11, 12.

What a successful redesign should demonstrate

These are proposed product acceptance checks and starting values, not measured usability outcomes or a claim of accessibility conformance. Validate the design with first-time users and actual phones.

  • From the homepage, a new visitor can find and start a named task without needing the sidebar explained. Observe task choice, wrong turns, and hesitation in a small usability session.
  • At 375, 390, 768, 1024, and 1440 px, the current task, selected file, required settings, and primary action form a coherent reading order with no clipped actions.
  • Every tool follows a recognizable empty, selected, processing, result, and recoverable-error pattern, with clear output details and Download again where a file is produced.
  • A token and component review confirms the same heading scale, spacing rhythm, action colors, control variants, focus treatment, and semantic states across all six families in both themes.
  • Keyboard-only and screen-reader checks cover selection, settings, processing, results, errors, and navigation. Real iOS and Android checks cover file picking, touch targets, redaction, soft keyboards, safe areas, and orientation.
  • First-time users can complete representative image, PDF, and video tasks and explain what happened to their file. Record completion, recovery, and confidence before and after the redesign rather than judging success from screenshots alone.

Detailed design critiques

P1 Mobile · Redaction and metadata Effort M

01 Essential actions are clipped outside the phone workspace

Observed

At 375 px, Pixelate extended to x=401, Emoji to x=481, and Download Without Metadata occupied x=401–663. The document width remained 375 px. The user sees a clipped toolbar, a partially visible Download, and no visible privacy-download action. Utilities metadata repeats the wide-action problem at 390 px.

Why it matters

A user can prepare a privacy edit and then fail to discover or reach the required export option. This blocks completion on phones and undermines the app's privacy purpose.

Recommended change

Make mode controls wrap or use a labeled mode selector. Stack export actions at narrow widths, shorten the privacy action to Remove metadata and download, and allow its label to wrap. Keep all actions within the content column; do not hide overflow to conceal an oversized row.

Acceptance criteria

At 375 and 390 px, every redaction mode and both export actions are fully visible and operable with no horizontal page pan or keyboard workaround. Repeat with an image selected in metadata and with long button labels.

P2 Mobile and tablet · Shared navigation Effort L

02 Navigation takes too much space at the breakpoints that need it most

Observed

The 64 px icon rail uses about 17% of a 375 px phone before content padding. At 768 px the full 288 px sidebar occupies 37.5% of the viewport. At 1024 px the sidebar and two-column tool layout leave an extremely narrow file panel, wrapping ordinary filenames across several lines.

Why it matters

Tasks feel cramped on tablets and phones even when the page has little actual content. Icon-only categories also make first-time navigation harder to understand.

Recommended change

Use a compact top app bar with a named Tools menu on phones. Keep tablet navigation collapsed until the workspace has enough width for both file and settings panels. Reserve the full sidebar for wide desktops, and consider expanding only the active category's tools.

Acceptance criteria

Review 375, 390, 768, 1024, and 1440 px layouts. The tool workspace should remain the dominant region. A tablet file row must fit a normal filename and its actions without forced multi-line fragmentation.

P2 Mobile · Shared file selection Effort M

03 The upload card stays oversized after selection

Observed

On a small phone the selected-image preview, nested borders, and padding consume most of the first screen. Tool tabs and settings follow below. PDF and archive screens similarly repeat selected-file information before the actual operation or results.

Why it matters

The user has completed file selection, but the layout continues giving that step the most space. Settings and completion actions require unnecessary scrolling, especially on a 667 px-tall phone.

Recommended change

After selection, collapse the upload area into a compact file summary with name, size, dimensions, Replace, and Remove. Make the preview expandable. Redaction should devote the main area to its editable canvas rather than showing the same image twice. Consider a compact sticky action area after controls are valid.

Acceptance criteria

On a 375 × 667 screen, the selected-file summary and the first useful task controls fit together in the initial viewport. Results should follow the task controls without another duplicate file-summary card.

P2 Mobile · Tool selection Effort M

04 The horizontal tab strip hides capabilities without explaining how to find them

Observed

Five image tabs share a narrow phone content column. Metadata and Resize are visible while later labels are cut off. Tabs measure about 27 px high. The page heading remains Image Tools, so the selected operation is communicated mainly by this small strip.

Why it matters

A new user may never discover Compress or Redact, and switching tools requires an unadvertised horizontal scroll or opening the global drawer.

Recommended change

Use a labeled tool selector or a wrapping tool grid on phones. Keep the active operation as the page title, such as Resize image. If scrolling tabs remain, provide clear overflow cues and ensure the active tab scrolls completely into view. Use a full-width grid only where all labels fit.

Acceptance criteria

At 375 px, all available tools are discoverable without guessing a swipe gesture. The current task name is visible independently of the tab strip, and labels are never cut mid-word.

P2 Desktop and mobile · Landing page Effort M

05 The landing page promotes project links before helping someone choose a task

Observed

The three prominent hero actions are View on GitHub, Report Issue, and Request Tool. The main content then explains client-side processing, WASM, open source, and release history. There is no main-content tool chooser or primary start action. On phones the first viewport contains project links and the beginning of a feature card.

Why it matters

Users must interpret the sidebar or unlabeled mobile icons to find the product's actual capabilities. The page explains implementation before helping a non-technical visitor accomplish something.

Recommended change

Keep the privacy promise, then offer a searchable or scannable set of task cards: Resize image, Compress video, Merge PDFs, Convert document to PDF, Create ZIP, and Verify a file. Move project/community links and release history below the task chooser. Put library details in an About section.

Acceptance criteria

At desktop and phone sizes, the initial screen provides an obvious route into at least the most common tasks. GitHub links remain available but have secondary visual weight.

P2 All tools · Completion and output Effort L

06 A successful download often leaves no visible result or useful comparison

Observed

After image resize, video compression, and PDF merge, the page largely returns to its prior controls with no persistent result card. The tested video grew from 203,313 to 210,600 bytes, about 3.6%, without a visible size comparison. Office does show success and output size, but its recovery action is Convert Again rather than Download again.

Why it matters

Users cannot easily confirm what changed, locate the result, or recover a missed download. A larger compression result can appear successful while failing the user's real goal of saving space.

Recommended change

Create a shared result panel with output name, type, dimensions or duration, before/after size, a clear Download action, Download again, and Process another file. Retain the generated result for re-download. If compression produces a larger file, say so and offer a sensible next step without claiming a size reduction.

Acceptance criteria

Every completed operation leaves a persistent, clearly labeled result. A user can re-download without rerunning WASM work. Compression reports positive or negative size change accurately.

P2 Video · Loading and processing Effort M

07 Importing a video is presented as an operation the user has not started

Observed

Immediately after selecting a WebM on the compression screen, the page showed Compressing Video, 0.0%, Cancel, and Compressing..., even though Compress Video had not been clicked. The state disappeared after metadata preparation finished.

Why it matters

The app seems to start encoding automatically, and the user cannot distinguish downloading tools, reading metadata, preparing a file, and performing the requested operation. A percentage that does not represent the active stage damages trust.

Recommended change

Model preparation and processing as distinct visible stages: Preparing video tools, Reading video information, Ready, and Compressing video. Show determinate progress only when the measurement belongs to that stage. Display Cancel only when it cancels the operation actually in progress.

Acceptance criteria

Selecting a video never claims compression has started. The label and progress indicator remain accurate through first-load, metadata extraction, encoding, success, and failure.

P2 Video · Trim Effort M

08 Trim starts in an invalid state and its presets can make that state worse

Observed

The tested three-second video opened Trim with an end time of ten seconds and an End time exceeds video duration error before any editing. Clicking First 30s set the end to thirty seconds rather than clamping it to the clip. The primary action remained disabled.

Why it matters

The user is asked to correct an error introduced by the interface. Manual HH:MM:SS fields also make a visual editing task feel unnecessarily technical.

Recommended change

Initialize the selection from zero to the actual duration. Hide, disable, or clamp presets that exceed the clip. Add a simple timeline with draggable in/out handles and keep precise time fields as an optional companion. Associate validation directly with the affected field.

Acceptance criteria

A valid short clip opens with a valid selectable range and no error. Every enabled preset produces a valid range. The user can choose a section without manually calculating timestamps.

P2 PDF · File selection and merge Effort S

09 The merge uploader contradicts the batch task

Observed

The empty state says Supports multiple PDF files, but the native picker was single-select. After one PDF, the only picker action was Change file; choosing another PDF appended it. Archive creation, by comparison, correctly uses a multiple-file picker.

Why it matters

Users cannot select their documents in one step, and the control suggests replacement when it actually adds another file. A two-file merge requires discovering an unexpected behavior.

Recommended change

Enable multi-select for PDF merging. Use Choose PDF files initially and Add PDFs after selection. Separate Replace and Remove actions where needed. Keep the current order preview, but add page counts and a clear total.

Acceptance criteria

A user can select two or more PDFs in one picker operation. Add PDFs preserves existing files, and no control labeled Change or Replace silently appends.

P2 Navigation · Working state Effort M

10 Leaving a category silently discards a working edit

Observed

After drawing a redaction, selecting Home and then using Back returned to an empty redaction screen. The image and drawn area were gone. No warning or recovery was offered.

Why it matters

Exploring the app can erase work. This is especially costly for multiple redactions or carefully configured tasks, and users may confuse a lost edit with a processing failure.

Recommended change

Keep the active workspace in memory across ordinary navigation, or warn when leaving a modified, unexported task. Give users an explicit Reset action. Avoid requiring persistent storage of file contents; the current browser session can retain state without uploading it.

Acceptance criteria

Home then Back either restores the selected file and edits or asks before discarding them. A completed download and an unexported modified file should be treated differently.

P2 Accessibility · Shared navigation and controls Effort M

11 Keyboard and assistive navigation carry avoidable friction

Observed

Tab traversal focused the Image Metadata link and then its nested button, followed by the Resize Image link and its nested button. The document exposed zero main and zero navigation landmarks. The drawer toggle is unnamed in the accessibility snapshot; collapsed category links have no link name in that snapshot. Several PDF drag/remove controls and video quality controls also lack clear accessible names.

Why it matters

Keyboard users traverse duplicate stops before reaching the task, while assistive users lack dependable structural shortcuts and names for important controls. The drawer's icon is a poor substitute for a meaningful action label.

Recommended change

Render each navigation item as a single styled link. Add navigation and main landmarks plus a skip-to-content link. Name the drawer toggle and expose its expanded state. Label every icon action and form control. Give PDF reordering clear move-up/down alternatives and human-readable announcements instead of raw draggable IDs.

Acceptance criteria

Each tool contributes one Tab stop. A keyboard user can skip navigation, open the picker, operate controls, and download. Accessibility snapshots expose meaningful names and landmarks, and PDF reordering is understandable without pointer input.

P2 Mobile · Touch ergonomics Effort S

12 Interactive controls are undersized for comfortable phone use

Observed

On the 375 px resize screen, tabs were 27 px high, Clear and Change file were 32 px high, the navigation toggle was 32 × 32 px, and Download was 36 px high. The visible checkbox control was 16 × 16 px, although its associated text provides an additional click target.

Why it matters

Small, closely packed controls increase precision demands when users are also handling a file picker, scrolling, or working one-handed. Tiny reorder and remove affordances add difficulty to batch tasks.

Recommended change

Use 44–48 px interactive rows and button targets for the phone layout, with sufficient separation. Expand checkbox and icon-button hit areas without enlarging every icon. Make drag handles and removal actions persistent and named on touch layouts.

Acceptance criteria

The primary phone controls have comfortable hit areas and spacing at 375 and 390 px. Confirm the result on actual touch devices; viewport geometry alone does not verify finger interaction.

P2 Images and video · Defaults and terminology Effort M

13 The default controls assume knowledge the target audience may not have

Observed

Video compression leads with Quality (CRF), a numeric scale, and Ultrafast. The helper calls 23 the default while the actual value is 28. Image resize initially shows empty fields with 800 and 600 placeholders even after loading a 350 × 208 image; Download stays disabled until a value is entered.

Why it matters

Non-technical users have to infer what a safe choice is and may mistake examples for active values. The apparent compression preset optimizes encoding speed without clearly expressing the effect on the goal of reducing size.

Recommended change

Lead with goal-based choices such as Smaller file, Balanced, and Higher quality, and move CRF/preset details into Advanced. Keep helper text consistent with the selected default. Prefill resize with actual dimensions and add percentage or common-size shortcuts. Use explicit action labels such as Resize and download PNG.

Acceptance criteria

A first-time user can choose an understandable default and produce an output without learning CRF. Numeric defaults match their explanatory text, and resize fields show actual values rather than misleading placeholders.

P2 Office · Error and recovery Effort S

14 Technical failure details are shown as the main explanation

Observed

A deliberately damaged DOCX produced: Conversion to Typst failed — no output received, followed by an unpacking error and end of central directory signature terminology. The primary retry action still offered Convert to PDF on the same damaged file.

Why it matters

The message exposes implementation details without telling a non-technical user whether they should retry, choose another file, or repair the document. Retrying the unchanged damaged input is unlikely to help.

Recommended change

Show a plain-language summary such as This document could not be opened. It may be damaged or may not be a valid DOCX file. Offer Choose another file and a specific repair suggestion. Put the original error in an expandable Technical details section. Use consistent success/error/loading components across tools.

Acceptance criteria

A damaged-file error identifies the likely user-facing problem and a useful next action. The full technical message remains available for issue reports without dominating the interface.

P2 Utilities · Hash results Effort S

15 Hashes are readable but unnecessarily difficult to reuse

Observed

MD5, SHA1, and SHA256 values are displayed as text without copy buttons. A matching expected hash shows a check and MD5, while a mismatch says No match. The layout wraps long hashes on phones, which is useful, but copying requires manual text selection.

Why it matters

Copying and comparing checksums is the purpose of the tool. Manual selection of 32–64 characters is tedious on a phone and invites partial copies. A positive match should be stated as clearly as a negative one.

Recommended change

Give each digest a named Copy action, brief Copied feedback, and an optional Copy all action. Say Matches MD5 or Does not match any calculated hash in a live status region. Keep selectable monospace text and show the full value on demand.

Acceptance criteria

Each complete checksum can be copied with one action. Verification produces explicit positive and negative messages, announced without moving focus. Confirm clipboard behavior on desktop and real mobile browsers.

P2 Utilities · Metadata relevance Effort S

16 The metadata screen offers irrelevant image guidance for a selected text file

Observed

For sample.txt, File Metadata shows MIME type and size, but a second EXIF Metadata card says Select an image file to view EXIF metadata and still offers Download Without Metadata. The interface does not explain what, if anything, would be removed from this text file.

Why it matters

The user has already selected a valid file, yet part of the page behaves as if the selection is missing. A privacy action without a clear scope can create false expectations about what it cleans.

Recommended change

Condition metadata panels on the selected file's capabilities. For a text file, show This file type has no image EXIF metadata instead of requesting another selection. Show removal actions only with a clear explanation of their scope, supported formats, and relevant metadata.

Acceptance criteria

A valid non-image selection has no contradictory Select an image instruction. Metadata removal explains its scope before the user invokes it, and irrelevant sections do not displace useful information.

P3 PDF · Capability availability Effort S

17 Unavailable tools have inconsistent affordances

Observed

Split and Compress are disabled in the PDF sidebar, but the same tools are enabled tabs. Selecting Split opens a Coming soon page while the user's files remain visible.

Why it matters

The interface gives conflicting answers about whether the task can be completed. Users can invest effort choosing files before discovering that a visible tool is unavailable.

Recommended change

Use one availability policy everywhere: hide unfinished tools from task navigation, or show an explicit Coming soon badge with a consistent non-actionable state. Keep release-roadmap information separate from the active processing workflow.

Acceptance criteria

Sidebar, tool chooser, and tabs communicate the same availability. A user does not enter a tool that looks operational and only then discover it has no implementation.

P3 Visual system · All surfaces Effort M

18 Visual hierarchy is dominated by containers rather than the task

Observed

Large shadows, rounded cards inside rounded cards, dashed borders around already-selected files, and generous repeated padding occupy much of each screen. Image Download is purple while most actions are blue and archive extraction is green. Office has a full-width single Convert tab. Dark mode retains a very bright pale error panel.

Why it matters

The interface feels heavier than its small control sets require, and action styling does not consistently communicate hierarchy. Decorative surface treatment consumes valuable mobile space and competes with result or error information.

Recommended change

Define a small set of surface, border, spacing, button, status, and typography tokens. Use one primary action treatment; reserve category color for navigation and status colors for outcomes. Remove redundant nested containers and single-option tabs. Give dark mode semantic error surfaces that fit its palette while remaining readable.

Acceptance criteria

A user can distinguish primary action, secondary action, input, and status consistently across all six families. Small screens lose redundant container padding, and light/dark states preserve the same information hierarchy.

P2 Mobile · Archive results Effort S

19 File rows sacrifice the information needed to choose the right download

Observed

At 390 px, the extraction list reduced 01-invoice.pdf to 01-in... and 02-project-notes.pdf to 02-p..., while the Download label retained most of the row width. These are short, ordinary filenames rather than an extreme stress test.

Why it matters

Users cannot confidently identify which file they are downloading. The problem grows with archives containing similar names or many files.

Recommended change

Put the full or wrapping filename on the first line and size plus a compact download action on the second. Preserve the extension and meaningful end of a truncated name. Give the action an accessible label containing the full filename and provide an easy way to reveal the complete name.

Acceptance criteria

At 375 and 390 px, ordinary filenames remain distinguishable and their extensions stay visible. Similar prefixes, long names, and multiple rows can be selected without relying on a desktop-only hover tooltip.
